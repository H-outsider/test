# MySQL 名词通俗解释

## 什么是 ACID？

ACID 是数据库用来保证**事务安全可靠**的四条规则。

事务可以理解为“必须一起完成的一组操作”。例如张三向李四转账 100 元，需要执行两步：

1. 张三的账户减去 100 元。
2. 李四的账户增加 100 元。

这两步必须作为一个整体执行，不能只扣钱却不到账。

### A：原子性（Atomicity）

原子性表示事务中的操作要么全部成功，要么全部失败，没有“只执行一半”的情况。

```sql
START TRANSACTION;

UPDATE account
SET balance = balance - 100
WHERE name = '张三';

UPDATE account
SET balance = balance + 100
WHERE name = '李四';

COMMIT;
```

如果第二条 `UPDATE` 执行失败，就使用 `ROLLBACK` 回滚。这样第一条语句扣掉的钱也会恢复：

```sql
ROLLBACK;
```

可以把原子性理解为：**转账要么完成，要么当作从未发生。**

### C：一致性（Consistency）

一致性表示事务执行前后，数据都必须符合数据库的规则。

例如转账前两个账户共有 1000 元，转账后总额仍应是 1000 元；如果账户规定余额不能小于 0，那么事务完成后也不能出现负数余额。

可以把一致性理解为：**操作完成后，账目仍然正确。**

### I：隔离性（Isolation）

隔离性表示多个事务同时执行时，应该尽量互不干扰。

例如张三正在向李四转账，但事务还没有提交，其他用户不应该看到“张三已经扣款、李四还未到账”这样的中间状态。

可以把隔离性理解为：**别人只能看到相对完整、符合隔离级别要求的操作结果，而不是随意看到操作到一半的数据。**

### D：持久性（Durability）

持久性表示事务一旦成功提交，修改结果就会被保存下来。即使数据库随后重启，已经提交的转账结果也不应该丢失。

```sql
COMMIT;
```

可以把持久性理解为：**数据库确认成功的事情，之后不能反悔。**

### 一句话记忆

- 原子性：要么全做，要么不做。
- 一致性：做完以后，数据仍然正确。
- 隔离性：同时操作时，彼此尽量不干扰。
- 持久性：提交以后，结果不会丢失。

## 什么是 BASE？

BASE 是一些分布式数据库常用的一种设计思想，名称来自三个英文短语：

- **Basically Available（基本可用）**：系统出现部分故障时，仍然尽量返回结果，而不是全部停止服务。
- **Soft State（软状态）**：数据状态可以暂时不是最终状态，系统允许数据在同步过程中发生变化。
- **Eventually Consistent（最终一致性）**：数据不会立刻在所有节点完全一致，但经过一段时间同步后，最终会一致。

例如电商下单后，订单服务可能先返回“下单成功”，再把库存和订单信息同步到其他服务。短时间内不同服务看到的数据可能不同，但同步完成后会恢复一致。

```text
用户下单
  -> 订单服务先保存订单并返回成功
  -> 消息队列通知库存服务扣减库存
  -> 其他服务陆续同步订单状态
  -> 最终所有服务看到一致结果
```

BASE 更关注分布式系统的可用性和扩展能力，常见于缓存、消息队列和部分 NoSQL 数据库。它不是“数据永远不一致”，而是接受短暂不一致，换取更好的可用性。

### ACID 和 BASE 的简单区别

ACID 更强调事务的强一致性和可靠性，适合转账、支付等核心交易；BASE 更强调系统在高并发和分布式环境下仍能提供服务，适合社交动态、商品浏览量等允许短暂延迟的数据。

## `NULL` 与索引、唯一约束和 `COUNT()` 有什么关系？

假设有一张用户表：

```sql
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(100) UNIQUE,
    age INT,
    INDEX idx_age (age)
);
```

### 1. `IS NULL` 也可能使用索引

MySQL 的 InnoDB 索引可以记录列中的 `NULL`，因此下面的查询可能通过 `idx_age` 找到年龄未填写的用户：

```sql
SELECT *
FROM users
WHERE age IS NULL;
```

是否真的走索引由优化器根据数据量和匹配行数决定。如果大部分数据的 `age` 都是 `NULL`，全表扫描反而可能更快。

### 2. 唯一索引可以允许多个 `NULL`

`email` 有唯一索引，相同的非空邮箱不能重复，但可以插入多个 `NULL`：

```sql
INSERT INTO users (id, email, age) VALUES (1, NULL, 20);
INSERT INTO users (id, email, age) VALUES (2, NULL, 25); -- 可以成功

INSERT INTO users (id, email, age) VALUES (3, 'a@example.com', 30);
INSERT INTO users (id, email, age) VALUES (4, 'a@example.com', 35); -- 重复键错误
```

这是因为 `NULL` 表示“未知”，MySQL 不把两个 `NULL` 当成相等的已知值。

### 3. `COUNT(字段)` 不统计 `NULL`

假设表中有 3 行数据，其中只有 2 行填写了 `age`：

```sql
SELECT COUNT(*) AS total, COUNT(age) AS age_count
FROM users;
```

结果可能是：

```text
total = 3
age_count = 2
```

`COUNT(*)` 统计所有行，`COUNT(age)` 只统计 `age` 不为 `NULL` 的行。因此，如果要统计“有多少个用户填写了年龄”，可以使用 `COUNT(age)`。

## `HAVING` 是什么？

`HAVING` 用于过滤 `GROUP BY` 分组后的结果，常和 `COUNT()`、`SUM()`、`AVG()` 等聚合函数一起使用。

例如，查询订单数量大于 3 的用户：

```sql
SELECT user_id, COUNT(*) AS order_count
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 3;
```

执行时先按 `user_id` 分组并统计每组的订单数，再由 `HAVING` 保留订单数大于 3 的分组。

`WHERE` 和 `HAVING` 的区别是：

- `WHERE` 在分组前过滤原始数据，不能直接用聚合函数作为条件。
- `HAVING` 在分组后过滤统计结果，可以使用聚合函数。

如果条件既可以写在 `WHERE` 也可以写在 `HAVING`，通常优先写在 `WHERE` 中，让数据在分组前就被过滤。

## 如何通俗理解 MySQL 可重入锁？

可以把一行锁记录想象成“房间门口的登记表”：

```text
lock_name       holder_id       reentry_count
order_lock      service-A-123   2
```

- `lock_name` 表示要保护的资源，例如订单处理锁。
- `holder_id` 表示现在是谁持有锁。
- `reentry_count` 表示同一个持有者重复加锁了多少次。

### 什么是“可重入”？

假设线程 A 已经获得了锁，它调用的另一个方法又请求同一把锁。如果锁不可重入，A 会等待自己释放锁，造成死锁。

可重入锁发现请求者仍然是 A 时，不会拒绝，而是将 `reentry_count` 从 1 加到 2。A 之后也必须解锁两次，计数减到 0 时才算完全释放。

### 加锁时发生了什么？

1. 开启事务，使用 `SELECT ... FOR UPDATE` 锁住这行登记记录。
2. 如果 `holder_id` 为空，就登记自己并将计数设为 1。
3. 如果 `holder_id` 是自己，就将计数加 1。
4. 如果锁属于其他人，就返回失败或稍后重试。
5. 提交事务。

`FOR UPDATE` 相当于在“登记表”前暂时排队，确保同一时刻只有一个请求能检查和修改这行数据。事务提交后，MySQL 的行锁会释放；但锁表中的 `holder_id` 仍然保留，它才表示业务锁仍被占用。

### 解锁时发生了什么？

解锁时也要用 `FOR UPDATE` 锁住记录，并先检查请求者是否就是持有者，防止别人误删锁：

- 计数大于 1：只将计数减 1，锁仍然属于当前持有者。
- 计数等于 1：将计数改为 0，并清空 `holder_id`，这时其他请求才能加锁。

### 为什么需要租约和续期？

如果持有者在释放锁前崩溃，MySQL 会释放数据库事务的行锁，但表里的 `holder_id` 不会自动清空，业务锁就可能永久被占用。

租约是给锁设置一个到期时间，持有者正常工作时定期续期；它崩溃后无法续期，其他请求就能在过期后重新获取锁。

### 为什么有过期时间还不够？

旧持有者可能只是暂时卡顿，锁过期并被新持有者抢走后，旧持有者又恢复执行。此时新旧两个请求都可能修改数据。

`fencing token` 是每次获取锁时递增的版本号，例如旧持有者拿到 10，新持有者拿到 11。被保护的资源只接受版本号更新的请求，因此旧持有者恢复后携带 10 号令牌的写入会被拒绝。

## `SELECT ... FOR UPDATE` 有什么作用？

### 最简单的理解

`FOR UPDATE` 就是：**我先查这条数据，而且接下来准备修改它，所以请让其他人先等一下。**

可以把它想成超市里只剩一件商品：你把商品拿在手里去结账时，别人不能同时拿走同一件。在你结账成功或放回商品之前，其他人只能等待。

### 例子：抢最后一张票

假设 100 号票还没有卖出：

```text
ticket_id = 100
status = '未售出'
```

如果小明和小红几乎同时查询，两人都可能看到“未售出”，然后都认为自己可以买，造成一张票卖给两个人。

小明的事务先执行：

```sql
START TRANSACTION;

SELECT status
FROM tickets
WHERE ticket_id = 100
FOR UPDATE;
```

小明查到“未售出”，同时锁住这张票的记录。此时小红也执行同样的 `FOR UPDATE` 查询，她不会立即得到结果，而是等待小明完成。

小明将票改为已售出并提交：

```sql
UPDATE tickets
SET status = '已售出'
WHERE ticket_id = 100;

COMMIT;
```

锁释放后，小红的查询继续执行。她看到票已经售出，就不会再购买。

因此，`FOR UPDATE` 不是立即修改数据，而是**在查询时先把记录占住，让“检查后再修改”这组操作不会被其他事务插队**。

### 技术上的作用

`FOR UPDATE` 将普通查询变成“锁定读”：在读取数据的同时，对相关记录加锁，防止其他事务在当前事务完成前修改或删除它们。

例如扣减商品库存：

```sql
START TRANSACTION;

SELECT stock
FROM products
WHERE id = 1
FOR UPDATE;

UPDATE products
SET stock = stock - 1
WHERE id = 1 AND stock > 0;

COMMIT;
```

第一个事务执行 `FOR UPDATE` 后，另一个事务如果想修改、删除或再次锁定这条商品记录，通常需要等待第一个事务执行 `COMMIT` 或 `ROLLBACK`。

普通的 `SELECT` 通常不会被阻塞，因为 InnoDB 可以通过 MVCC 读取已提交的历史版本。

`FOR UPDATE` 应放在显式事务中使用，否则语句结束后锁就会很快释放，无法保护后续操作。它具体锁住哪些记录与索引、查询条件和事务隔离级别有关；范围查询还可能产生间隙锁或临键锁。

## 什么是聚簇索引？

### 先用一句话理解

在 InnoDB 中，**聚簇索引就是一棵叶子节点直接保存完整行数据的 B+ 树**。通常它就是主键索引。

### 档案柜的例子

假设学校有一个学生档案柜，档案按学号从小到大排列。柜子的目录帮你逐步找到对应学号，找到最后，里面放的不是另一个地址，而是这个学生的完整档案。

```text
上层目录：              100  |  200
                         /       |       \
底层档案： [1, 小明, 20] ... [100, 小红, 21] ... [200, 小刚, 22]
```

这就是“聚簇”的含义：**索引的叶子节点和真正的行数据聚在一起**。

### 在 InnoDB 中是怎样的？

假设有一张表：

```sql
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    age INT,
    INDEX idx_name (name)
) ENGINE = InnoDB;
```

`id` 是主键，所以 InnoDB 会用 `id` 组织聚簇索引。它的叶子节点保存完整数据：

```text
主键聚簇索引的叶子节点：

id=1   -> [1, '小明', 20]
id=5   -> [5, '小红', 21]
id=9   -> [9, '小刚', 22]
```

执行下面的查询时，MySQL 沿着主键 B+ 树找到 `id = 5` 的叶子节点，就能直接拿到整行数据：

```sql
SELECT * FROM students WHERE id = 5;
```

### 辅助索引为什么需要“回表”？

`idx_name` 是辅助索引。它的叶子节点通常保存的是“姓名 + 主键值”，而不是完整行：

```text
姓名辅助索引：

'小明' -> id=1
'小红' -> id=5
'小刚' -> id=9
```

执行：

```sql
SELECT age FROM students WHERE name = '小红';
```

MySQL 需要进行两次查找：

1. 先在 `idx_name` 中找到小红的主键 `id = 5`。
2. 再回到主键聚簇索引中，根据 `id = 5` 找到完整行，取出 `age`。

第二步就叫“回表”。如果查询只需要辅助索引中已经保存的列，就可以直接返回，这种情况叫“覆盖索引”，不需要回表。

### 为什么一张表只能有一个聚簇索引？

因为表中的行数据只能按一种主要顺序组织。就像一堆学生档案，可以按学号顺序排列，也可以按姓名顺序排列，但不能让同一份原始档案同时保持两种排列方式。

一张表可以有很多辅助索引，但只有一棵索引树的叶子节点直接保存完整行数据，所以只能有一个聚簇索引。

### 没有主键时怎么办？

InnoDB 需要找到一个值来组织聚簇索引，大致选择顺序是：

1. 优先使用显式定义的主键。
2. 没有主键时，选择第一个所有列都不允许为 `NULL` 的唯一索引。
3. 两者都没有时，InnoDB 自动生成隐藏的行 ID。

因此，InnoDB 表通常应主动设计合适的主键。

### 聚簇索引对主键设计有什么影响？

- **主键不宜过大**：辅助索引的叶子节点会保存主键值，主键越大，所有辅助索引占用的空间也越大。
- **主键尽量有序**：自增主键通常向 B+ 树尾部追加数据；完全随机的主键可能导致更多页分裂和页移动。
- **主键范围查询高效**：叶子节点按主键顺序连接，查询连续主键范围时可以顺序读取。

需要注意，“按主键组织”指的是 B+ 树的逻辑顺序，不表示所有行在磁盘物理位置上必然完全连续。

## `db.opt`、`.frm` 和 `.ibd` 分别存储什么？

这三个不是“三张表”，而是 MySQL 5.7 数据目录中的三类文件。可以把它们理解为：

```text
db.opt       = 数据库的默认设置
t_order.frm  = t_order 表的结构说明书
t_order.ibd  = t_order 表的数据和索引仓库
```

假设创建了如下数据库和表：

```sql
CREATE DATABASE my_test
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_general_ci;

CREATE TABLE my_test.t_order (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20),
    INDEX idx_user_id (user_id)
) ENGINE = InnoDB;
```

### 1. `db.opt`：数据库级别的默认设置

`db.opt` 是较简单的配置文件，在这个例子中可以逻辑地理解为：

```text
default-character-set=utf8mb4
default-collation=utf8mb4_general_ci
```

之后在 `my_test` 中创建表时，如果没有为表单独指定字符集和排序规则，就会继承这里的默认值。它不保存表结构，也不保存订单数据。

### 2. `t_order.frm`：表结构的二进制说明书

`.frm` 是 MySQL 5.7 使用的二进制表定义文件，不是可以直接当作 SQL 文本打开的 `CREATE TABLE` 语句。

它逻辑上记录的是：

```text
表名：t_order
存储引擎：InnoDB

字段：
- id       BIGINT，主键，自增
- user_id  BIGINT，不允许为 NULL
- amount   DECIMAL(10, 2)，不允许为 NULL
- status   VARCHAR(20)

索引：
- PRIMARY KEY (id)
- idx_user_id (user_id)
```

它只说明“表应该长什么样”，不保存 `id = 1001` 这样的真实订单记录。

### 3. `t_order.ibd`：按页组织的表数据和索引

开启 `innodb_file_per_table` 后，`t_order.ibd` 是这张 InnoDB 表的独立表空间。它是二进制文件，内部按页管理，默认页大小通常为 16 KB。

可以将它的逻辑结构简化为：

```text
t_order.ibd
├── 表空间管理信息
├── 空间分配信息和空闲页
├── 主键聚簇索引 B+ 树
│   └── 叶子页保存完整订单行
├── user_id 辅助索引 B+ 树
│   └── 叶子页保存 user_id 和主键 id
└── 较长字段可能使用的溢出页
```

假设插入一条订单：

```sql
INSERT INTO my_test.t_order (id, user_id, amount, status)
VALUES (1001, 20, 99.90, 'PAID');
```

在 `.ibd` 中可以逻辑地理解为：

```text
主键聚簇索引叶子页：
1001 -> [1001, 20, 99.90, 'PAID']

idx_user_id 辅助索引叶子页：
20 -> 1001
```

根据 `id = 1001` 查询时，可以在主键聚簇索引中直接取得完整行。根据 `user_id = 20` 查询时，先从辅助索引取得主键 `1001`，再根据主键回表查找完整行。

### `ibdata1` 和 `.ibd` 的关系

- `innodb_file_per_table = 1`：新建表的数据和索引通常保存在各自的 `.ibd` 文件中。
- `innodb_file_per_table = 0`：表的数据和索引可以保存在 `ibdata1` 等系统表空间文件中，不会为每张表创建独立 `.ibd`。

`ibdata1` 不只是某一张表的文件，它是 InnoDB 的系统表空间文件，还承担系统级结构的存储。

### MySQL 8.0 的变化

MySQL 8.0 取消了 `.frm` 和 `db.opt` 这类基于文件的元数据存储，表结构、数据库默认属性等信息改由事务型数据字典管理。独立表空间的 `.ibd` 文件仍然存在。

## 哈希表取模后，相邻数值不是会放进相邻的桶吗？

如果为了演示直接使用下面的简单函数：

```text
bucket = key % 10
```

那么 18～22 的桶号确实是：

```text
18 -> 桶 8
19 -> 桶 9
20 -> 桶 0
21 -> 桶 1
22 -> 桶 2
```

它们在一小段范围内看起来近似顺序，但到 20 时就从桶 9 回到了桶 0。而且每隔 10 的值会落到同一个桶：

```text
桶 8: 8, 18, 28, 38, ...
桶 9: 9, 19, 29, 39, ...
桶 0: 0, 10, 20, 30, ...
```

因此按桶号从 0 读到 9，得到的并不是键值从小到大的顺序。如果要查询 `18 <= age <= 22`，不能只读一段连续且有序的桶，还要在桶内区分 8、18、28 等哈希冲突的值。

真实哈希表通常还会先计算更复杂的哈希值，再根据桶数取模：

```text
bucket = hash(key) % bucket_count
```

哈希函数会尽量将数据均匀分散到各个桶，相邻键值更不保证落到相邻桶。哈希表只保证“同一个键每次都能算到对应的桶”，不保证桶号与键的大小顺序一致。

## 什么是磁盘页？它和数据库行数有什么关系？

磁盘页可以理解成 InnoDB 存取数据时使用的固定大小“盒子”。InnoDB 不会为了查询一行只从磁盘读取这一行，而是把这一行所在的整个页读入 Buffer Pool；修改时也先修改内存中的页，之后再把脏页刷回磁盘。InnoDB 常见的默认页大小是 16 KB。

一个数据页通常包含多行记录以及页头、页目录、记录管理信息和空闲空间。因此，页和行不是一一对应关系：一页能放多少行取决于行大小和页面开销。行较小时一页可以放很多行，行较大时只能放少量行；`TEXT`、`BLOB` 等大字段还可能把部分内容存到页外。

例如，忽略各种页面和记录开销进行粗略理解：16 KB 的页最多可以容纳约 160 条 100 字节记录，却只能容纳约 16 条 1 KB 记录，真实数量通常更少。所以行数增加一般会使数据页数量增加，但不能只根据行数准确计算页数，还要考虑行宽、索引、页填充率、删除和页分裂造成的碎片等因素。

在 InnoDB 的 B+ 树中，一个节点通常对应一个索引页：非叶子页保存导航键和子页指针，叶子页保存索引记录。查询一行时，B+ 树先定位其所在页，再通过页目录和页内记录链表找到具体记录。
