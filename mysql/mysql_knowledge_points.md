# MySQL 面试题

## 1.1 NoSQL 和 SQL 有什么区别？

SQL 数据库是关系型数据库，如 MySQL、PostgreSQL、Oracle 和 SQL Server。数据通常以二维表存储，具有固定的数据结构，可以通过外键和 `JOIN` 表达数据之间的关系，适合事务要求高、数据关系复杂的场景。

NoSQL 是非关系型数据库的统称，如 Redis 和 MongoDB。它可以使用键值、文档、列族或图等模型存储数据，数据结构通常更灵活，适合高并发、海量数据和分布式扩展场景。

两者的主要区别如下：

- **数据模型**：SQL 以关系表为主；NoSQL 支持键值、文档等多种模型。
- **事务与一致性**：SQL 通常强调 ACID 和强一致性；许多 NoSQL 系统更注重可用性与扩展性，可能采用 BASE 和最终一致性，但这不是绝对的，部分 NoSQL 也支持事务和强一致性。
- **扩展方式**：SQL 通常优先纵向扩展，分库分表后需要处理跨库查询和分布式事务；NoSQL 通常更容易通过分片进行水平扩展。
- **适用场景**：金融交易、订单等强事务场景通常优先选择 SQL；缓存、会话、日志和高并发读写等场景可以考虑 NoSQL。

实际项目中二者并非只能选择一个，常见做法是使用 SQL 保存核心业务数据，同时使用 Redis 等 NoSQL 数据库承担缓存或高并发访问。

## 1.2 数据库三大范式是什么？

数据库范式是设计关系型数据库表结构的一组规范，主要目的是减少数据冗余和更新异常。常见的三大范式如下：

### 第一范式（1NF）

要求每一列都是不可再分的原子值，不能在一个字段中保存一组数据。

例如，不要把多个电话号码写在同一个 `phone` 字段中，而应拆成独立记录或独立字段，使每个单元格只保存一个值。

### 第二范式（2NF）

在满足 1NF 的基础上，要求所有非主键列都完全依赖于整个主键，不能只依赖联合主键的一部分。

例如订单明细表使用 `(order_id, product_id)` 作为联合主键时，`quantity` 依赖整个联合主键；但 `order_time` 只依赖 `order_id`，应拆到订单表中，避免重复保存。

### 第三范式（3NF）

在满足 2NF 的基础上，要求非主键列不能依赖其他非主键列，也就是消除传递依赖。

例如学生表中，`student_id -> teacher_name -> teacher_phone`。教师电话应放到教师表中，学生表只保存 `teacher_id`，避免教师信息重复。

### 面试中的简便记忆

- 1NF：字段不可再分。
- 2NF：非主键列完全依赖整个主键。
- 3NF：非主键列不能依赖其他非主键列。

范式可以减少冗余并避免插入、更新、删除异常，但范式越高，表拆分通常越多。实际项目会根据查询性能和业务需要，在规范化与适度反规范化之间做取舍。

## 1.3 MySQL 怎么进行联表查询？

联表查询使用 `JOIN` 根据两个表之间的关联字段组合数据，常见类型如下。假设员工表 `employees.department_id` 关联部门表 `departments.id`：

### 1. 内连接（`INNER JOIN`）

只返回两个表中能够匹配的记录：

```sql
SELECT e.name AS employee_name, d.name AS department_name
FROM employees AS e
INNER JOIN departments AS d
  ON e.department_id = d.id;
```

### 2. 左外连接（`LEFT JOIN`）

返回左表的全部记录。右表没有匹配时，右表字段为 `NULL`：

```sql
SELECT e.name AS employee_name, d.name AS department_name
FROM employees AS e
LEFT JOIN departments AS d
  ON e.department_id = d.id;
```

这可以查出所有员工，包括尚未分配部门的员工。

### 3. 右外连接（`RIGHT JOIN`）

返回右表的全部记录。左表没有匹配时，左表字段为 `NULL`：

```sql
SELECT e.name AS employee_name, d.name AS department_name
FROM employees AS e
RIGHT JOIN departments AS d
  ON e.department_id = d.id;
```

这可以查出所有部门，包括暂时没有员工的部门。实际开发中通常改写表的顺序后使用 `LEFT JOIN`，可读性更好。

### 4. 全外连接（`FULL JOIN`）

全外连接会返回两张表的所有记录，包括双方无法匹配的记录。MySQL 不直接支持 `FULL JOIN`，可以使用 `LEFT JOIN` 和 `RIGHT JOIN` 组合实现：

```sql
SELECT e.name AS employee_name, d.name AS department_name
FROM employees AS e
LEFT JOIN departments AS d
  ON e.department_id = d.id

UNION

SELECT e.name AS employee_name, d.name AS department_name
FROM employees AS e
RIGHT JOIN departments AS d
  ON e.department_id = d.id;
```

其中 `UNION` 会去除完全重复的行；如果使用 `UNION ALL`，则需要额外过滤已匹配的记录，避免重复结果。

### 简单记忆

- `INNER JOIN`：只要匹配的。
- `LEFT JOIN`：左表全部保留。
- `RIGHT JOIN`：右表全部保留。
- `FULL JOIN`：两边全部保留，MySQL 需组合实现。

## 1.4 MySQL 如何避免重复插入数据？

### 1. 使用 `UNIQUE` 唯一约束

在需要保证唯一的列上建立唯一索引或唯一约束，由数据库从根本上防止重复数据：

```sql
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(255) NOT NULL UNIQUE,
    name VARCHAR(255)
);
```

当插入相同的 `email` 时，MySQL 会返回重复键错误。这是保证数据唯一性的基础方案。

### 2. `INSERT ... ON DUPLICATE KEY UPDATE`

如果遇到重复键，不报错，而是更新已有记录，适合“插入或更新”（upsert）：

```sql
INSERT INTO users (email, name)
VALUES ('example@example.com', 'John Doe')
ON DUPLICATE KEY UPDATE name = 'John Doe';
```

### 3. `INSERT IGNORE`

遇到重复键时忽略本次插入，其他可插入的数据仍可继续处理：

```sql
INSERT IGNORE INTO users (email, name)
VALUES ('example@example.com', 'John Doe');
```

需要注意，`INSERT IGNORE` 可能同时忽略部分数据校验错误，不应在不了解影响的情况下滥用。

### 如何选择？

- 必须保证唯一：使用 `UNIQUE` 约束。
- 重复时需要更新：使用 `ON DUPLICATE KEY UPDATE`。
- 重复时直接跳过：使用 `INSERT IGNORE`。

## 1.5 `CHAR` 和 `VARCHAR` 有什么区别？

- **`CHAR`**：固定长度字符串。定义长度后，每个值按固定长度存储，不足部分通常用空格补齐，适合身份证号、固定长度编码、状态码等长度稳定的数据。
- **`VARCHAR`**：可变长度字符串。定义的是最大长度，实际占用空间取决于字符串实际长度，并额外保存长度信息，适合姓名、地址、备注等长度不固定的数据。

例如：

```sql
code CHAR(6),        -- 固定长度编码
nickname VARCHAR(50) -- 最多 50 个字符的昵称
```

简单来说，`CHAR` 读取长度固定、适合短小且长度稳定的值；`VARCHAR` 更节省可变文本的存储空间。选择类型时还要结合字符集，因为 `VARCHAR(n)` 的实际最大字节数会受到字符集影响。

## 1.6 `VARCHAR` 后面的数字代表字节还是字符？

在 MySQL 中，`VARCHAR(n)` 的 `n` 表示**最多可以存储的字符数**，不是字节数。

```sql
nickname VARCHAR(10)
```

这表示最多存储 10 个字符。实际占用的字节数取决于字符集：

- ASCII 字符通常每个占 1 个字节，10 个字符约占 10 个字节。
- `utf8mb4` 字符每个最多占 4 个字节，10 个字符最多可能占 40 个字节，另外还需要保存长度信息。

因此，`VARCHAR(10)` 既可以存 10 个英文字母，也可以存 10 个中文字符；但中文通常占用更多字节。设计表结构时还要注意 MySQL 单行最大字节数等限制。

## 1.7 `INT(1)` 和 `INT(10)` 在 MySQL 中有什么区别？

`INT(1)` 和 `INT(10)` 的括号数字不是取值范围，也不会改变 `INT` 的存储大小。普通 `INT` 始终占用 4 个字节，取值范围也相同：

```sql
CREATE TABLE test_int (
    num1 INT(1),
    num2 INT(10)
);
```

历史上，这个数字被称为“显示宽度”，配合 `ZEROFILL` 时可以在显示时补前导零：

```sql
CREATE TABLE test_int (
    num1 INT(1) ZEROFILL,
    num2 INT(10) ZEROFILL
);

INSERT INTO test_int VALUES (1, 1);
-- 旧版本客户端可能显示：1、0000000001
```

它不会限制可以存入的数字，也不会把数字截断。MySQL 8.0.17 起，整数类型的显示宽度已被弃用，`ZEROFILL` 也不建议用于新设计，因此不要用 `INT(1)` 表示只能存 0 或 1；需要限制取值时，应使用 `TINYINT`、`CHECK` 约束或业务逻辑。

## 1.8 `TEXT` 数据类型可以无限大吗？

不能。MySQL 的 `TINYTEXT`、`TEXT`、`MEDIUMTEXT` 和 `LONGTEXT` 最大容量分别约为 255 字节、64 KB、16 MB 和 4 GB。

这些上限按字节计算，因此使用 `utf8mb4` 时实际可存储的字符数更少。实际读写还受 `max_allowed_packet` 等限制，大文件通常应放在对象存储中，数据库只保存地址。

## 1.9 金额为什么建议用 `DECIMAL`，而不是 `FLOAT` 或 `DOUBLE`？

`DECIMAL` 保存精确的十进制数，`FLOAT` 和 `DOUBLE` 保存近似值，可能产生精度误差，因此金额通常使用 `DECIMAL`。

例如 `DECIMAL(10, 2)` 表示最多 10 位数字，其中 2 位是小数。也可以用 `BIGINT` 保存“分”等最小货币单位；应用程序同样要使用精确类型并明确舍入规则。

## 1.10 IP 地址如何在数据库里存储？

IPv4 可以用 `VARCHAR(15)` 直接保存，直观但占用空间较多、不便于范围查询；也可以转换为 `INT UNSIGNED`，配合 `INET_ATON()` 和 `INET_NTOA()` 读写，存储和比较更高效。

如果还要支持 IPv6，可以统一使用 `VARBINARY(16)`，配合 `INET6_ATON()` 和 `INET6_NTOA()`；这两个函数也支持 IPv4。

## 1.11 说一下外键约束

外键用于维护表之间的引用完整性，保证子表引用的父表记录真实存在。例如多对多关系通常通过中间表保存两张表的外键。

删除或更新父表记录时，可以使用 `RESTRICT` 拒绝操作、`CASCADE` 级联处理，或用 `SET NULL` 将外键置空。外键能让数据库自动校验关系，但会增加检查和加锁开销；不使用外键时，需要由应用保证数据一致性。

## 1.12 MySQL 的关键字 `IN` 和 `EXISTS`

`IN` 用于判断某个值是否属于一个列表或子查询结果集；`EXISTS` 只判断子查询是否至少返回一行，不关心返回的具体内容。

两者的性能取决于索引、数据分布和执行计划，不能简单记成“大表用 `EXISTS`、小表用 `IN`”。需要特别注意：`NOT IN` 的结果集中如果包含 `NULL`，条件可能变为 `UNKNOWN`；查询“不存在关联记录”的数据时，通常优先使用 `NOT EXISTS`。

## 1.13 MySQL 中常用的基本函数有哪些？

- **字符串函数**：`CONCAT()` 拼接字符串，`SUBSTRING()` 截取子串，`REPLACE()` 替换内容。`LENGTH()` 返回字节数，`CHAR_LENGTH()` 返回字符数。
- **数值函数**：`ABS()` 求绝对值，`POWER()` 计算幂。
- **日期时间函数**：`NOW()` 返回当前日期和时间，`CURDATE()` 返回当前日期。
- **聚合函数**：`COUNT()` 计数，`SUM()` 求和，`AVG()` 求平均值，`MAX()` 和 `MIN()` 分别求最大值和最小值。

需注意，`COUNT(*)` 统计结果集的行数，而 `COUNT(column)` 不统计该列为 `NULL` 的行。

## 1.14 `COUNT(*)`、`COUNT(1)` 和 `COUNT(字段)` 有什么区别？

- `COUNT(*)`：统计结果集的行数，不受某一列是否为 `NULL` 影响。
- `COUNT(1)`：对每行统计常量 1，结果与 `COUNT(*)` 相同。
- `COUNT(字段)`：只统计该字段不为 `NULL` 的行。

InnoDB 需要根据事务的可见性扫描数据，不能直接返回固定总行数。通常不必为了性能把 `COUNT(*)` 改成 `COUNT(1)`；要表达“统计行数”时优先使用 `COUNT(*)`。大表频繁统计且允许延迟时，可以考虑维护汇总数据。

## 1.15 `NULL` 和空字符串有什么区别？

`NULL` 表示值未知或缺失，空字符串 `''` 表示值已知但内容为空，两者不相等。判断 `NULL` 要使用 `IS NULL` 或 `IS NOT NULL`，普通比较遇到 `NULL` 通常会得到 `UNKNOWN`；MySQL 的 `<=>` 可以进行 `NULL` 安全比较。

`NULL` 并不代表无法使用索引，`IS NULL` 也可能走索引。另外，唯一索引通常允许多个 `NULL`，`COUNT(字段)` 不会统计 `NULL`。

## 1.16 `DELETE`、`TRUNCATE` 和 `DROP` 有什么区别？

- `DELETE`：删除表中的记录，可以带 `WHERE` 条件，保留表结构。InnoDB 中可以在事务提交前回滚，并会逐行触发 `DELETE` 触发器。
- `TRUNCATE`：清空整张表，不能带 `WHERE`，保留表结构，通常会重置自增计数器，不会逐行触发 `DELETE` 触发器。
- `DROP`：删除整张表，表结构和数据都不再保留。

`TRUNCATE` 和 `DROP TABLE` 属于 DDL，会隐式提交，不能像普通事务那样通过 `ROLLBACK` 撤销。MySQL 8.0 的原子 DDL 主要保证崩溃恢复时操作的一致性。

## 1.17 SQL 查询语句的执行顺序是怎样的？

SQL 查询的逻辑处理顺序为：

```text
FROM / JOIN → ON → WHERE → GROUP BY → HAVING
→ SELECT → DISTINCT → ORDER BY → LIMIT
```

因此，`WHERE` 过滤分组前的记录，`HAVING` 过滤分组后的结果。`SELECT` 中定义的别名通常不能在 `WHERE` 中使用，但 MySQL 允许在 `GROUP BY`、`HAVING` 和 `ORDER BY` 中使用。

这是逻辑顺序，不是数据库内部的固定执行步骤。优化器可能调整连接顺序、提前过滤或利用索引避免排序。

## 1.18 SQL 题：查询不存在 01 课程但存在 02 课程的学生成绩

假设学生表为 `Student(sid, sname)`，成绩表为 `Score(sid, cid, score)`，可以先查出 02 课程成绩，再用 `NOT EXISTS` 排除选了 01 课程的学生：

```sql
SELECT s.sid, s.sname, sc.cid, sc.score
FROM Student AS s
JOIN Score AS sc
  ON s.sid = sc.sid AND sc.cid = '02'
WHERE NOT EXISTS (
    SELECT 1
    FROM Score AS sc1
    WHERE sc1.sid = s.sid AND sc1.cid = '01'
);
```

也可以分别左连接 01 和 02 课程记录，再通过“01 为 `NULL`、02 不为 `NULL`”进行筛选。

## 1.19 SQL 题：查询总分排名在 5～10 名的学生及总分

给定 `student_score(stu_id, subject_id, score)`，可以先按学生求总分，再使用窗口函数排名：

```sql
WITH student_totals AS (
    SELECT stu_id, SUM(score) AS total_score
    FROM student_score
    GROUP BY stu_id
),
ranked_students AS (
    SELECT
        stu_id,
        total_score,
        RANK() OVER (ORDER BY total_score DESC) AS ranking
    FROM student_totals
)
SELECT stu_id, total_score
FROM ranked_students
WHERE ranking BETWEEN 5 AND 10
ORDER BY ranking, stu_id;
```

该写法需要 MySQL 8.0 及以上版本。`RANK()` 允许并列且会跳号，`DENSE_RANK()` 允许并列但不跳号；如果只需要排序后的第 5～10 条记录，可以使用 `ROW_NUMBER()` 并增加 `stu_id` 作为稳定的排序条件。

## 1.20 SQL 题：查询某个班级下所有学生的选课情况

假设有学生表 `students`、选课表 `course_selections` 和班级表 `classes`，查询 `Class A` 所有学生的选课情况：

```sql
SELECT
    s.student_id,
    s.student_name,
    cs.course_name
FROM students AS s
JOIN classes AS c
  ON s.class_id = c.class_id
LEFT JOIN course_selections AS cs
  ON s.student_id = cs.student_id
WHERE c.class_name = 'Class A';
```

选课表必须使用 `LEFT JOIN`，这样没有选课的学生也会被返回，其 `course_name` 为 `NULL`。如果还要限制选课表的数据，通常应将条件写在 `ON` 中，避免在 `WHERE` 中过滤掉未匹配的学生。

## 1.21 如何用 MySQL 实现一个可重入的锁？

可以建立锁表，使用唯一的 `lock_name` 标识锁，并记录 `holder_id` 和 `reentry_count`。加锁时在事务中通过 `SELECT ... FOR UPDATE` 锁定记录：

- 锁空闲时，将持有者设为自己，重入次数设为 1。
- 持有者是自己时，将重入次数加 1。
- 持有者是其他请求时，加锁失败或等待重试。

解锁时同样使用 `FOR UPDATE` 并校验持有者：重入次数大于 1 时减 1，等于 1 时清空持有者并完全释放锁。`holder_id` 应包含实例和线程等唯一信息，不能只使用线程名。

这种实现还需要处理持有者崩溃后锁无法释放的问题。生产环境通常需要加入租约、续期和 fencing token 等机制，仅设置过期时间不能完全避免过期持有者继续写入。

## 1.22 执行一条 SQL 请求的过程是什么？

MySQL 执行一条 SQL 的主要流程如下：

1. **连接器**：建立和管理连接，完成身份认证与权限校验。
2. **解析器**：对 SQL 进行词法和语法分析，构建语法树。
3. **预处理器**：检查表和字段是否存在，并展开 `SELECT *` 等内容。
4. **优化器**：评估索引、连接顺序等方案的成本，选择执行计划。
5. **执行器**：按照执行计划调用存储引擎读写数据，再将结果返回客户端。

旧版本还有查询缓存，命中时可以直接返回结果，但 MySQL 8.0 已经删除该功能。

## 1.23 讲一讲 MySQL 的存储引擎

- **InnoDB**：MySQL 的默认存储引擎，支持 ACID 事务、行级锁、外键和崩溃恢复，适合大多数高并发读写场景。
- **MyISAM**：使用表级锁，不支持事务和外键，并发写入和故障恢复能力较弱。它是早期常用引擎，新业务通常优先选择 InnoDB。
- **Memory**：数据保存在内存中，访问速度快，但服务器重启或崩溃后数据会丢失，且不支持事务、行级锁和外键，适合临时数据等特定场景。

## 1.24 MySQL 为什么将 InnoDB 作为默认引擎？

InnoDB 在事务支持、并发性能和崩溃恢复方面更适合现代业务系统：

- **事务支持**：支持 ACID 事务，可以保证多步操作的完整性，而 MyISAM 不支持事务。
- **并发性能**：支持行级锁和 MVCC，多个事务可以更高效地并发读写；MyISAM 主要使用表级锁。
- **崩溃恢复**：通过 redo log 等机制，可以在断电或异常宕机后恢复已提交的数据。

因此，InnoDB 在数据可靠性、一致性和高并发方面更均衡，适合大多数业务场景。

## 1.25 InnoDB 与 MyISAM 有什么区别？

- **事务**：InnoDB 支持 ACID 事务和崩溃恢复，MyISAM 不支持事务。
- **索引结构**：InnoDB 的主键索是聚簇索引，叶子节点保存行数据，辅助索引保存主键值；MyISAM 的索引和数据分开存储，索引保存数据记录的位置。因此 InnoDB 的主键不宜过大，否则会增大所有辅助索引。
- **锁粒度**：InnoDB 支持行级锁，并发读写能力较强；MyISAM 主要使用表级锁，并发写入能力较弱。
- **`COUNT(*)`**：InnoDB 需要统计当前事务可见的记录；MyISAM 保存表的总行数，无 `WHERE` 的简单计数可以直接返回，但有过滤条件时仍需扫描数据。

## 1.26 MySQL 的数据文件大体分为哪几种？

以 MySQL 5.7、InnoDB 独立表空间为例，数据库目录中常见的文件有：

- **`db.opt`**：保存数据库的默认字符集和排序规则。
- **`.frm`**：保存表结构等元数据，每张表通常对应一个文件。
- **`.ibd`**：独立表空间文件，保存 InnoDB 表的数据和索引。
- **`ibdata1`**：InnoDB 系统表空间文件；未使用独立表空间时，表数据也可能存放在其中。

`innodb_file_per_table` 控制新建表是否使用独立 `.ibd` 文件。MySQL 8.0 已取消 `.frm` 文件，表结构等元数据改由事务型数据字典管理，但独立表空间的 `.ibd` 仍保存表数据和索引。数据目录可通过 `SHOW VARIABLES LIKE 'datadir'` 查看。

## 1.27 Buffer Pool 是什么？有什么作用？

Buffer Pool 是 InnoDB 的内存缓冲区，主要缓存从磁盘读取的数据页和索引页，可以理解为磁盘数据在内存中的“工作区”。

- **查询**：页在 Buffer Pool 中时直接读取，未命中时才从磁盘加载，从而减少磁盘 I/O。
- **更新**：通常先修改内存页，被修改的页称为脏页，之后由后台线程刷回磁盘。
- **提交**：利用 redo log 的 WAL 机制，事务提交时通常不需等待所有脏页立即刷盘。

Buffer Pool 缓存的是数据页，不是 SQL 查询结果，与 MySQL 8.0 已删除的查询缓存不同。InnoDB 还使用分为新、老区域的改进 LRU 策略，避免大表扫描轻易淘汰大量热点页。

## 1.28 索引是什么？有什么好处？

索引是一种用空间换时间的数据结构，类似书籍目录，可以帮助 MySQL 快速定位数据，避免扫描整张表。InnoDB 的常规索引主要使用 B+ 树。

索引不仅能加快 `WHERE` 和 `JOIN` 查询，还可以辅助排序、分组，并通过覆盖索引减少回表。但索引会占用存储空间，并增加 `INSERT`、`UPDATE` 和 `DELETE` 的维护成本；查询返回大量数据时，即使使用索引也不一定快。

## 1.29 MySQL 索引有哪些分类？

MySQL 索引可以从四个角度分类：

- **按数据结构**：B+Tree 索引、Hash 索引、Full-Text 全文索引。
- **按物理存储**：聚簇索引和二级索引。InnoDB 聚簇索引的叶子节点保存完整行，二级索引的叶子节点保存索引列和主键值。
- **按字段特性**：主键索引、唯一索引、普通索引、前缀索引。
- **按字段数量**：单列索引和联合索引。

InnoDB 通常使用主键组织聚簇索引；没有主键时，尝试选择所有列都为 `NOT NULL` 的唯一索引，否则生成隐藏行 ID。

联合索引按索引列的先后顺序排列，使用时要关注最左匹配原则。例如 `(a, b, c)` 通常可用于 `a`、`a+b`、`a+b+c` 的前缀定位；跳过 `a` 时通常无法按常规前缀快速定位。范围条件后的列可能无法继续缩小扫描范围，但仍可用于索引下推或覆盖索引，最终以执行计划为准。

## 1.30 哈希索引的使用场景是什么？

哈希索引通过哈希函数将索引键映射到对应的桶，适合以精确等值查询为主的场景，平均查找效率可以接近 `O(1)`。例如 Memory 存储引擎中根据用户 ID 查询临时状态或权限信息。

哈希索引不保留键的大小顺序，因此不适合范围查询、排序、分组和最左前缀匹配。它还需要处理哈希冲突，所以查找效率并非在任何情况下都绝对是 `O(1)`。InnoDB 的常规索引主要是 B+Tree，其自适应哈希索引由引擎内部自动管理。

## 1.31 MySQL 聚簇索引和非聚簇索引有什么区别？

- **聚簇索引**：InnoDB 使用它组织整张表，B+ 树的叶子节点保存完整行数据，因此一张表只能有一个。通常由主键充当；没有合适主键时，InnoDB 会选择符合条件的唯一索引或生成隐藏行 ID。
- **非聚簇索引（二级索引）**：叶子节点保存索引列和对应的主键值，一张表可以创建多个。
- **查询区别**：使用聚簇索引可以直接取得整行；使用二级索引查询其未包含的列时，要先取得主键，再到聚簇索引中查找完整记录，这叫回表。如果所需字段已全部包含在二级索引中，则形成覆盖索引，不需要回表。
- **使用特点**：聚簇索引适合按主键查询和主键范围扫描；二级索引适合按其他字段快速查找，但大量回表可能增加随机 I/O。是否更快还取决于查询字段、返回行数和执行计划，不能一概而论。

## 1.32 MySQL 主键是聚簇索引吗？

需要看存储引擎。对于 **InnoDB**，主键索引就是聚簇索引，其 B+ 树叶子节点保存完整行数据，记录按主键在叶子页中有序组织，但不代表磁盘页物理连续。

InnoDB 选择聚簇索引键的顺序是：

1. 有主键时使用主键。
2. 没有主键时，选择第一个所有索引列均为 `NOT NULL` 的唯一索引。
3. 两者都没有时，生成一个 6 字节的隐藏行 ID。

一张 InnoDB 表只有一个聚簇索引，其他索引都是二级索引，叶子节点保存索引列和聚簇键。MyISAM 等存储引擎的索引组织方式不同，因此不能笼统地说 MySQL 的所有主键都是聚簇索引。

## 1.33 什么字段适合当作主键？

适合当主键的字段应当满足：

- **唯一且非空**：能够稳定标识一行数据。
- **短小**：InnoDB 的二级索引会保存主键值，主键越宽，索引占用和维护成本越高。
- **稳定**：主键不应频繁修改，避免数据移动以及所有二级索引中的主键值随之更新。
- **尽量递增**：新记录通常追加到 B+ 树尾部，可减少随机插入导致的页分裂和碎片；但并非绝对不能使用非递增主键。

一般不建议直接使用订单号、手机号等可能变化或复用的业务字段作为主键，可以将其设置为唯一索引，另用无业务含义的 ID 作为主键。单机系统常用 `BIGINT AUTO_INCREMENT`；分布式系统需要统一规划 ID，可使用号段、雪花类算法或有序 UUID 等方案，避免不同节点产生重复主键。

## 1.34 性别字段能加索引吗？为什么？

可以加，但性别的取值种类少、选择性通常较低，单列索引往往收益不大。例如男女各占约一半时，`SELECT *` 查询其中一类需要通过二级索引命中大量记录并逐条回表，成本可能高于全表扫描，优化器可能因此不使用该索引。

低选择性字段并非一定不能建索引，以下情况仍可能有效：

- 数据分布不均匀，并且查询的是占比很小的一类。
- 查询字段都能由索引提供，形成覆盖索引，例如按性别统计数量。
- 与其他查询条件建立联合索引，例如 `(sex, age)` 支持按性别查询指定年龄范围。

是否创建和使用索引，应结合查询条件、数据分布、返回比例、回表成本，并通过 `EXPLAIN` 和实际测试判断。

## 1.35 表中有十个字段，主键使用自增 ID 还是 UUID？为什么？

字段数量不是选择依据。对于常规单库 InnoDB 表，通常优先使用 `BIGINT AUTO_INCREMENT`：它短小且递增，新记录大多追加到聚簇索引右侧，索引占用较小，也能减少随机 I/O、页分裂和碎片；二级索引保存的主键也更小。

随机 UUID 通常占用空间更大，插入位置分散，可能使目标页频繁换入 Buffer Pool，并增加页分裂和碎片。如果以字符串形式存储，空间和比较成本还会进一步增加。

不过，自增 ID 不便于多个独立节点直接生成全局唯一值，也可能暴露数据规模。需要跨节点生成、离线写入或合并数据时，可以使用号段、雪花类 ID 或有序 UUID；UUID 可考虑紧凑的二进制存储。不能把所有 UUID 都视为完全随机，最终应结合系统架构选择。

## 1.36 为什么自增 ID 通常比 UUID 写入快？UUID 在 B+ 树中有序吗？

UUID 插入 B+ 树后同样会按索引比较规则保持有序，区别在于随机 UUID 的**生成顺序**通常与索引顺序不同，新记录可能插入不同的中间叶子页；自增 ID 通常比现有最大值更大，新记录大多顺序追加到最右侧叶子页。

因此，自增 ID 的写入局部性通常更好，更容易命中 Buffer Pool 中的热点页，并能减少随机读页、页分裂和碎片。同时，`BIGINT` 只有 8 字节，而 UUID 字符串更宽；主键越宽，聚簇索引和保存主键值的所有二级索引占用越大。

UUID 可以使用 `BINARY(16)` 缩小空间，也可以采用大致按时间递增的 UUID 方案改善插入局部性。自增 ID 也可能发生页分裂和并发竞争，只是常规 InnoDB 写入场景下通常更友好。

## 1.37 自增主键一定连续吗？

不一定。自增只负责自动分配 ID，并在正常约束下避免重复，不保证最终保存的 ID 连续。事务取得 ID 后回滚、插入因其他约束失败、删除已有记录，以及并发或批量插入中的 ID 分配，都可能留下空洞，已经消耗的值通常不会回收重用。

自增 ID 的分配顺序也不等于事务提交顺序：事务 A 可以先取得 `100`，事务 B 后取得 `101`，但 B 可能先提交。因此，不能根据 ID 是否连续判断数据是否丢失，也不能直接把 ID 大小当成严格的业务发生或完成顺序；需要业务顺序时应保存相应的时间或序列字段。

## 1.38 MySQL 中的索引是怎么实现的？

索引实现取决于存储引擎和索引类型。最常用的 InnoDB 普通索引使用 B+ 树：它是多叉平衡树，非叶子节点主要保存索引键和子页指针，用于导航；叶子节点保存全部索引记录，并按键值有序，相邻叶子页通过双向链表连接，适合等值和范围查询。

- **聚簇索引**：通常按主键组织，叶子节点保存完整行数据。
- **二级索引**：叶子节点保存索引列和主键值；查询索引未覆盖的字段时，需要用主键回表。

查询时从根页开始，根据键值逐层选择子页，直到叶子页找到记录。B+ 树分叉数大，通常层数较少；实际磁盘 I/O 取决于树高、页面是否命中 Buffer Pool、是否回表及扫描范围，不能把树高直接当成整条查询固定的 I/O 次数。

除 B+ 树外，MySQL 还有全文、空间等索引；Memory 引擎可以使用 Hash 索引，InnoDB 也可能在内部维护自适应哈希索引，因此不能笼统地说所有 MySQL 索引都由 B+ 树实现。

## 1.39 到达 B+ 树叶子节点后，InnoDB 如何查找具体记录？

InnoDB 的叶子节点对应数据页。页内记录按索引键有序，并通过单向链表连接；为避免从头遍历，数据页还维护了页目录。页目录把记录分组，每个槽（slot）保存一组中最大记录的页内偏移量，该记录的 `n_owned` 表示它管理的记录数量。

页内查找过程是：

1. 对页目录中的槽进行二分查找，定位目标可能所在的记录组。
2. 从前一槽指向的记录开始，沿页内单向链表扫描少量记录，找到目标或确认不存在。

聚簇索引叶子页按主键排序，二级索引叶子页按二级索引键和主键值排序。要注意，B+ 树相邻叶子页之间使用双向链表，而同一页中的记录之间使用单向链表。被标记删除但尚未由 purge 清理的记录仍可能暂时存在于页内结构中。

## 1.40 B+ 树有哪些特性？

- **多叉且层数少**：一个非叶子节点可以保存多个索引键和子页指针，分叉数大，相同数据量下通常比二叉树更矮，能减少定位记录需要访问的页面层数。
- **数据集中在叶子层**：非叶子节点主要用于导航，查找最终都会到达叶子节点。InnoDB 聚簇索引的叶子节点保存完整行，二级索引的叶子节点保存索引列和主键值。
- **叶子节点等高、有序相连**：所有叶子节点位于同一层并按索引键排序；InnoDB 相邻叶子页通过双向链表连接，适合范围扫描，也可能为符合索引顺序的排序查询省去额外排序。
- **自平衡**：插入或删除可能引起节点分裂、合并或重新组织，使各叶子节点继续保持在同一层，树高维持稳定，因此等值查找的层级复杂度通常为 `O(log N)`。

B+ 树节点的最低占用和分裂细节取决于具体定义与数据库实现，面试中重点说明其多叉、平衡、数据位于叶子层及叶子有序相连即可。

## 1.41 B+ 树和 B 树有什么区别？

- **数据位置**：B 树的内部节点和叶子节点都可以保存数据记录；B+ 树的内部节点主要保存分隔键和子节点指针，全部索引记录集中在叶子节点。
- **查找路径**：B 树查找可能在内部节点提前命中；B+ 树通常必须走到叶子节点，因此不同键的树内定位层数更稳定。
- **范围查询**：B+ 树的叶子节点有序相连，定位范围起点后可以沿链表连续扫描；B 树通常需要在树结构中继续进行中序遍历。
- **分叉和树高**：B+ 树内部节点不保存完整记录，同样大小的页面通常能放入更多键和子指针，分叉数更大、树高更低，更适合数据库按页读写。

因此，B 树可能在等值查询时提前找到记录，而 B+ 树在磁盘 I/O、范围扫描和批量顺序访问方面更适合数据库索引。InnoDB 的普通索引主要采用 B+ 树。

## 1.42 B+ 树有什么好处？

- **树高较低**：非叶子节点主要保存索引键和子页指针，同样大小的页面能够容纳更多分支，因此树更“矮胖”，定位记录通常只需访问较少层页面。
- **适合按页读写和缓存**：完整索引记录集中在叶子层，内部页只负责导航，结构与数据库按页存储、读取和在 Buffer Pool 中缓存的方式契合。
- **范围扫描高效**：叶子节点按索引键有序并通过链表连接，定位范围起点后可以沿叶子页连续扫描，也有利于符合索引顺序的排序和顺序访问。
- **性能较稳定**：所有叶子节点位于同一层，树始终保持平衡，单条记录的树内定位层数相对稳定。

B+ 树的插入和删除仍可能触发页分裂、合并及父节点调整，不能认为每次修改都比 B 树快。它的主要优势是综合兼顾等值查询、范围扫描和磁盘页面访问，因此适合 InnoDB 索引。

## 1.43 B+ 树的叶子节点链表是单向还是双向？

在 InnoDB 中，相邻的 B+ 树叶子页通过双向链表连接，每个页都能找到前一页和后一页，因此可以向前或向后进行范围扫描，也有利于符合索引顺序的正序、倒序读取。是否能避免 `ORDER BY` 的额外排序，还要看查询条件与索引顺序是否匹配。

要区分两个层次：叶子**页之间**是双向链表，同一数据页中的记录按索引键组成的是单向链表，并通过页目录辅助定位。InnoDB 数据页默认大小通常是 16 KB。

聚簇索引叶子页保存完整行，一张 InnoDB 表只有一个聚簇索引；二级索引叶子页保存索引列和主键值，可以创建多个。

## 1.44 MySQL 为什么使用 B+ 树？与其他结构相比有什么优点？

准确地说，InnoDB 的普通索引主要使用 B+ 树，因为它适合数据库按页读写，并能综合支持等值查询、范围查询和顺序扫描。

- **对比 B 树**：B+ 树内部节点主要保存索引键和子页指针，同样大小的页面能容纳更多分支，树通常更矮；叶子页有序相连，范围扫描也更方便。
- **对比平衡二叉树**：B+ 树是多叉树，分叉数远大于 2，相同数据量下层数更少，能减少磁盘页面访问。
- **对比 Hash**：Hash 适合等值查询，平均查找效率可接近 `O(1)`，但不保留键值顺序，不适合范围查询、排序和前缀匹配；B+ 树的适用场景更全面。

B+ 树也有维护成本，插入和删除可能引起页分裂、合并。实际 I/O 还取决于 Buffer Pool 命中、树高、回表次数和扫描范围，不能把理论层数直接当成固定磁盘 I/O 次数。
